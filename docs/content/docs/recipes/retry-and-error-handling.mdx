## Configure handler retries

Use `@WithRetry` to set the attempt budget and backoff for a handler. The [Durable Lambda adapter](/docs/plugins/durable-lambda#retry-integration) and [retry-aware custom adapters](/docs/recipes/custom-adapter#retry-only-classified-handler-failures) use that configuration. `orchestrator.transit()` always runs one attempt, even with `@WithRetry`.

See [payment processing with retry](/docs/examples/payment-with-retry) for handler examples.

### Configuration

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `handler` | `string` | Required | Name of the handler method |
| `maxAttempts` | `number` | Required | Positive safe integer. Counts the initial attempt. |
| `strategy` | `RetryStrategy` | `EXPONENTIAL_JITTER` | Backoff strategy |
| `initialDelay` | `number` | `1000` | Base delay in milliseconds |
| `backoffMultiplier` | `number` | `2` | Multiplier applied on each attempt |
| `maxDelay` | `number` | `60000` | Cap on the exponential delay before jitter, in milliseconds |
| `jitter` | `boolean \| number` | `true` | `true` for full jitter, `0-1` for partial jitter percentage |

## Backoff strategies

NestflowJS supports three retry strategies via the `RetryStrategy` enum:

### `RetryStrategy.FIXED`

The delay is `initialDelay` between attempts.

### `RetryStrategy.EXPONENTIAL`

The delay is `min(maxDelay, initialDelay * backoffMultiplier ** attempt)`. The first retry uses `attempt = 0`.

### `RetryStrategy.EXPONENTIAL_JITTER` (default)

The adapter varies the exponential delay to spread out retries.

- With `jitter: true`, the delay is uniformly random between zero and the capped exponential delay.
- With `jitter: 0.5`, the delay varies by up to 50% in either direction around the capped exponential delay. The final delay can exceed `maxDelay`.

## Classify failures

An adapter starts another attempt only when `transitAttempt()` returns `{ status: 'retry' }`. It keeps the same `eventId` and increments `attempt`.

| Outcome | What happens |
|---------|--------------|
| Handler throws `UnretriableException` | The orchestrator commits the configured failed state and returns `{ status: 'final', state: failedState }`. The adapter does not retry. |
| Handler throws another error and attempts remain | The orchestrator releases the claim without advancing the state or writing a completion receipt. It returns `{ status: 'retry' }`. |
| Handler throws another error on the last attempt | The orchestrator commits the configured failed state and an exhaustion receipt, then propagates the handler error. A later delivery of the same event reports exhaustion without rerunning the handler. |
| Validation, a guard, storage, or post-commit processing throws | The error propagates without an adapter retry. If the failure occurs after commit, the committed transition stays in place. |
| Another transition holds the entity's claim | The orchestrator raises `ConflictException`. NestJS maps it to HTTP `409 Conflict`. |

Throw `UnretriableException` in the handler for a known permanent failure, such as a payment provider declining the payment. See the [payment example](/docs/examples/payment-with-retry) for the difference between a decline and an error eligible for a retry.

## Make side effects idempotent

If the worker stops before committing, the storage lease can expire and a later delivery can run the handler again. Use `@EventId()` with the entity ID as the idempotency key for external writes. Keep guards pure. The orchestrator can evaluate them again without rerunning a committed handler.

Return only serializable data you can safely persist. A completion receipt stores the handler output and the entity snapshot. Do not put secrets or raw payment credentials in either.

## Validate payloads

Validate incoming event payloads before your handler executes. NestflowJS accepts your schema library. Guards can see the payload before handler validation, so handle unvalidated input in guards.

### Setup

Provide a `payloadValidator` function when registering the module:

```typescript
import { WorkflowModule } from 'nestflow-js/core';
import { zodPayloadValidator } from '@nestflow-js/validator-zod';

@Module({
  imports: [
    WorkflowModule.register({
      entities: [{ provide: 'entity.payment', useClass: PaymentEntityService }],
      workflows: [PaymentWorkflow],
      payloadValidator: zodPayloadValidator,
    }),
  ],
})
export class PaymentModule {}
```

### Use `@Payload()`

Pass your schema to `@Payload()`:

```typescript
import { z } from 'zod';

const SubmitPaymentSchema = z.object({
	amount: z.number().positive(),
	currency: z.string().length(3),
	paymentMethodId: z.string(),
});

@OnEvent('payment.initiated')
async handleInitiated(
  @Entity() payment: Payment,
  @Payload(SubmitPaymentSchema) data: z.infer<typeof SubmitPaymentSchema>,
) {
  // data is validated and typed
  return { amount: data.amount };
}
```

If validation fails, the framework throws a `BadRequestException` wrapping the validation error.

For Valibot, ArkType, or Joi, register the [matching validator plugin](/docs/api-reference/interfaces#payloadvalidator) and pass its schema to `@Payload(schema)`.

## Calculate a backoff delay

For custom retry logic outside of `@WithRetry`, use the `RetryBackoff` utility directly:

```typescript
import { RetryBackoff, RetryStrategy } from 'nestflow-js/core';

const delay = RetryBackoff.calculateDelay(attempt, {
  handler: 'myHandler',
  maxAttempts: 5,
  strategy: RetryStrategy.EXPONENTIAL_JITTER,
  initialDelay: 1000,
  backoffMultiplier: 2,
  maxDelay: 30000,
  jitter: true,
});

// Alternative: decorrelated jitter
const nextDelay = RetryBackoff.decorrelatedJitter(previousDelay, 1000, 30000);
```
