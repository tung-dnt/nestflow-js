title: Events and Handlers
description: Events trigger state transitions. Handlers run your business logic when a transition fires. NestflowJS discovers and wires everything automatically.

## Event identity

Every [`IWorkflowEvent`](/docs/api-reference/interfaces#iworkflowevent) has an `eventId`. Reuse the ID for retries and redeliveries of the same event. Never reuse it for a different event on the same entity. Auto-continuations have their own stable IDs, supplied in `nextEvent`.

## @OnEvent

`@OnEvent` binds a method to an event name. The orchestrator runs the handler after it acquires a claim and finds a valid transition:

```typescript
@OnEvent('order.submit')
async onSubmit(@Entity() order: Order) {
	return { orderId: order.id };
}
```

The orchestrator stores the handler output in the transition receipt. If the workflow continues automatically, the output becomes the next event's payload. Return only serializable data that is safe to persist.

**Constraint:** Event names must be globally unique across all workflow classes. Duplicate `@OnEvent` handlers for the same event throw at startup.

## Parameter Injection

### @Entity()

Injects the entity snapshot from the transition claim:

```typescript
@OnEvent('order.submit')
async onSubmit(@Entity() order: Order) {
  console.log('Processing order:', order.id);
  return order;
}
```

### @Payload(schema?)

Injects the event payload. Optionally pass a schema for validation:

```typescript
@OnEvent('order.submit')
async onSubmit(
  @Entity() order: Order,
  @Payload(SubmitOrderDto) data: SubmitOrderDto,
) {
  // data is validated via the PayloadValidator provided in WorkflowModule.register()
  return order;
}
```

### @EventId()

Injects the stable delivery ID. Combine it with the entity ID for downstream idempotency when calling a payment service or another system with side effects. A crash before the transition commits can cause the handler to run again.

If the handler has no parameter decorators, it receives `{ entity, payload }` as a single argument.

## @OnDefault

Runs before `BadRequestException` when a known event has no valid transition. If guards reject an otherwise matching transition in an idle state, the orchestrator returns `idle` instead.

```typescript
@OnDefault
async fallback(entity: Order, event: string, payload?: any) {
  console.warn(`Unhandled event: ${event} for order ${entity.id}`);
  return entity;
}
```

One per workflow class. No parentheses needed.

## Auto-Discovery

You don't manually register handlers. When NestJS initializes:

1. `OrchestratorService` implements `OnModuleInit`
2. Scans all providers via `DiscoveryService.getProviders()`
3. Reads `@Workflow` metadata from each class
4. Reads `@OnEvent` metadata for handler registrations
5. Resolves entity services via `ModuleRef.get()` using the DI token
6. Builds a routing table: event name → handler + definition + entity service

This is fully automatic — decorate your classes, register them in `WorkflowModule.register()`, and everything is wired.
