## The storage contract

The orchestrator uses [`IWorkflowEntity.claimTransition(urn, eventId)`](/docs/api-reference/interfaces#iworkflowentity) instead of separate `load()` and `update()` calls. Check for a receipt and acquire the claim atomically with respect to concurrent deliveries. A claim is exclusive per entity. A receipt deduplicates an event by entity and event ID.

Persistence methods return cold Observables. Each subscription performs one operation, emits its single result, and completes. `release()` and recovery acknowledgement emit `undefined` on success. With a Promise-based driver, use `defer(() => driverCall())` so no I/O starts before subscription.

- If there is a receipt for the event, return it with `kind: 'completed'`. The orchestrator uses the saved snapshot and does not run the handler again.
- If the entity does not exist, return `kind: 'missing'`.
- If another owner holds a live claim, return `kind: 'busy'`. The orchestrator raises `ConflictException` (HTTP 409).
- Otherwise, acquire a lease and return `kind: 'acquired'` with the entity snapshot, `commit()`, and `release()`.

`commit(state, completion)` must verify the owner's token, persist the updated entity and receipt, and clear the claim in one atomic operation. After takeover, the earlier owner cannot commit. `release()` must only clear the caller's own claim.

The receipt must hold the entity snapshot as it was at commit, not a pointer to the latest entity state. Retain receipts for as long as events can be redelivered. Persist only serializable entity snapshots and handler output that are safe to store.

Coordinate any other writers of workflow state with the same claim. A separate `load()` followed by an unconditional `update()` cannot protect against concurrent writes.

## Recovery after a crash

If the process crashes before commit, a later delivery can acquire the expired lease and run the handler again. An atomic commit does not guarantee exactly-once side effects. Use [`@EventId()`](/docs/api-reference/decorators#eventid) and the entity ID as a downstream idempotency key.

See the [DynamoDB entity service](https://github.com/tung-dnt/nestflow-js/blob/main/examples/lambda-order-state-machine/src/order/order-entity.service.ts) for a storage-backed implementation.

## Registration

Entity services are registered via DI tokens in `WorkflowModule.register()`:

```typescript
WorkflowModule.register({
  entities: [
    { provide: 'entity.order', useClass: OrderEntityService },
  ],
  workflows: [OrderWorkflow],
})
```

The token string (`'entity.order'`) must match the `entityService` field in your `@Workflow` definition.
