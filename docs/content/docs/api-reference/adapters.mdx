## TransitResult

On success, `orchestrator.transit()` returns a `TransitResult`. It runs one attempt and does not schedule retries.

### Type Definition

```typescript
import type { Duration, IWorkflowEvent } from 'nestflow-js/core';

type TransitResult =
  | { status: 'final'; state: string | number }
  | { status: 'idle'; state: string | number; timeout?: Duration }
  | { status: 'continued'; nextEvent: IWorkflowEvent }
  | { status: 'no_transition'; state: string | number; timeout?: Duration };
```

| Status | Meaning | What to do |
|--------|---------|-----------|
| `final` | The entity reached a terminal state, or the handler threw `UnretriableException` and committed the failure state. | End the workflow. |
| `idle` | Entity is in an idle state, waiting for external input. | Wait for a callback or poll a queue. Optional `timeout` hints how long. |
| `continued` | The orchestrator found an automatic continuation. | Pass `nextEvent` through unchanged, including its `eventId`. |
| `no_transition` | No unambiguous auto-transition from the current state. | Wait for an explicit event from an external system. |

Use the [`IWorkflowEvent`](/docs/api-reference/interfaces#iworkflowevent) envelope for each new event. Supply the same event ID on retries and redelivery.

## Node and message workers

Import these functions from `nestflow-js/adapter`. They use the same registered Nest `OrchestratorService` as the Lambda adapter.

- `runInProcess(orchestrator, event)` follows automatic continuations. It returns when the result is `final`, `idle`, or `no_transition`. To resume a paused workflow, submit a new event for the same entity.
- `processWorkflowMessage(orchestrator, raw)` validates the decoded workflow envelope and executes one logical transition, including configured handler retries. It returns the result without publishing or acknowledging a message.
- `recoverNextTransition(orchestrator, store, deliver)` claims a pending committed transition and derives its result without calling the original handler. It acknowledges the claim only after `deliver(result)` resolves. It returns `false` when the store offers no work.

Each broker factory accepts `consume`, an async function that processes a decoded event. Pass `raw => processWorkflowMessage(orchestrator, raw)` when the entity store commits pending work in the transition transaction. A separate dispatcher publishes automatic continuations. The factory does not open connections or start a polling process.

| Factory and options | Inbound delivery | Outbound delivery |
| --- | --- | --- |
| `createRabbitMQAdapter({ channel, queue, consume })` | `consumeOne()` reads at most one message from the queue. It returns `false` when the queue is empty. | `publish(event)` uses an application-owned confirm channel and rejects an unroutable mandatory publish. |
| `createAzureServiceBusAdapter({ sender, connection, queueName, consume })` | Register `trigger` with `app.serviceBusQueue(name, trigger)`. `connection` is the **setting name**, not its secret value. | `publish(event)` awaits `sender.sendMessages`. |
| `createGcpPubSubAdapter({ topic, subscription, consume })` | Pass an authenticated, decoded push envelope to `consumePush`. Send its returned HTTP status. Return a non-success response for thrown errors. | `publish(event)` awaits the topic's `publishMessage`. |

The [deployment guide](/docs/deployment-architecture) covers message settlement, retry clocks, and storage requirements.

## BaseWorkflowAdapter

`runWorkflowLoop(initialEvent, ctx)` invokes `executeTransit()` and dispatches the result. A subclass implements these hooks:

| Hook | Returns |
|------|---------|
| `executeTransit(event, iteration, ctx)` | `Promise<TransitResult>` |
| `onFinal(result, event, ctx)` | The adapter's final `TResult` |
| `onIdle(result, event, iteration, ctx)` | `Promise<IWorkflowEvent>` after an external event arrives |
| `onContinued(result, iteration, ctx)` | `Promise<IWorkflowEvent>` with the supplied `nextEvent` |
| `onNoTransition(result, event, iteration, ctx)` | `Promise<IWorkflowEvent>` after an explicit event arrives |

`ctx` is the adapter's `TContext`. `iteration` starts at zero and advances after each loop result, not after each handler retry. Each hook that takes `result` receives the corresponding `TransitResult` variant.

## Retries and delivery errors

An adapter can call [`transitAttempt(event, canRetry)`](/docs/api-reference/services#transitattempt) to support `@WithRetry`. Pass `true` only when another attempt remains. Retry only on `{ status: 'retry' }`. Keep the same `eventId` and increment `attempt`. Validation, guard, storage, and post-commit errors propagate instead of requesting a retry.

The orchestrator raises `ConflictException` (HTTP 409) when the entity has a live claim and the event has no receipt. A delivery system can requeue the original event with backoff. A custom HTTP adapter must validate its input before passing it to the orchestrator. A queue adapter must preserve the producer's logical event ID across redeliveries.

## DurableWorkflowEvent

```typescript
interface DurableWorkflowEvent {
	urn: string | number;
	initialEvent: string;
	eventId: string;
	payload?: unknown;
}
```

The producer supplies a non-blank `eventId` for the initial event and reuses it on redelivery. Callback bodies still contain `event` and an optional `payload`. The adapter derives stable IDs for callbacks. The orchestrator derives stable IDs for automatic continuations.

The adapter does not use SDK automatic retries for transit steps. It schedules the next attempt only when `transitAttempt()` returns `{ status: 'retry' }`.

Drain in-flight executions before you change their replay behavior. If you deploy a new version while executions are still running, keep those executions on the old version until they finish.
